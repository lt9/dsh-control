# 05 故障排查

面向排障现场的操作手册。架构约束在 `ARCHITECTURE.md`（§5.4 是 nginxWebUI），这里只放
"出了事怎么查、动手前怎么核对"。

## 库盘一致性核对（跑 `/api/nginx/replace` 之前必做）

`replace` 是全面板按库重建：`conf.d` 整目录重写、**库里没有的 conf 文件会被删掉**
（§5.4 红线）。库里任何与磁盘不一致的值都会被打回磁盘，所以重建前必须核对。

**控制台侧没有替代品的能力边界**：这一版 nginxWebUI 不提供任何读配置文件内容的接口
（`getFileContent` / `getFile` / `fileContent` / `confContent` 实测全 404），控制台也
没有 VPS 的 SSH。因此**磁盘真相只有运维只读比对一条路**，`drift_scan` 只能当旁证
（见下）。

### 运维只读比对（真正能证明一致性的做法）

1. 库侧：面板 API 分页读 `getPage` / `getLocationByServerId`（或运维直读 sqlite，
   `mode=ro`），取每条 location 的 `header_host`。
2. 盘侧：只读 `cat`/`grep` conf.d，取每个 server 文件里的 `proxy_set_header Host`。
3. 按站点名配对逐条比对。库里没有对应文件的（未发布/停用）与文件在库找不到的
   （**会被 replace 删除**）要单独列出。
4. 有漂移：只走面板把库改对（或确认盘上的手改是要保留的并回填库），绝不动文件系统。

最近一次实测（2026-10）：65 个 conf 文件、21 站点 + 25 upstream，可比对 10 条，
**0 漂移**——但前提是当时尚未有人手改；这条核对必须在每次 `replace` 前重做。

### `drift_scan` 黑盒旁证的口径与边界

控制台在 `replace` 前会跑 `drift_scan`：`https://<站点>/api/healthz` 带 `Origin` 探测，
与库里 `header_host` 对表。**状态码只有能证明后端是 DSH 时才是证据**：

- 证明通道只有两条：编排层传入的 `known_dsh` 登记名单；或响应带家族信封指纹
  （200 `{"ok": true}` / 401 `{"ok": false, "error": …}`，见 §4.1 错误清单）。
  真 DSH 的脏 Host 403 是裸文本，**不能**凭体证明，只能靠登记通道。
- 非 DSH 后端不是证据源：jellyfin/Gogs/llamaServer 拿到带端口的 Host 照样回
  200/401/502；onlyOffice 自家回 403。曾按状态码硬判，把三条库盘一致的
  `$host:$proxy_port` 站点误报成漂移（假警报），也把 onlyOffice 的 403 判成
  "一致"（假安全感）——两类错误都已修，证明不了的一律 `inconclusive`。
- 判定口径（全部以"后端已证明是 DSH"为前提）：`db_dirty`（库脏 + 探到 401/200，
  **盘净**——replace 会把好盘洗坏）· `dirty_both`（库脏 + 探到 403，**盘同脏**——
  replace 中性，但该站点此刻公网正被准入墙拦住）· `disk_dirty`（库净 + 探到 403，
  人手改过磁盘，replace 能纠正回库值）· `consistent` · `inconclusive` ·
  `unreachable` · `no_location`；默认只体检本控制台站点，他人站点仅在
  `all_sites=True` 时列库值不判定。
- 危险列表 = `db_dirty` / `dirty_both` / `disk_dirty` 三值；`dsh_proven=false` 一律
  `inconclusive`，不进危险列表。要下结论就回到上面的运维比对。处置对照：

  | verdict | 含义 | 处置 |
  |---|---|---|
  | `db_dirty` | replace 会把好盘洗坏 | **急**：先 `patch_location` 把库改成 `$host`（会自动 reload 生效），再允许 replace |
  | `dirty_both` | 库盘一致，站点当前公网被准入墙拦住 | **不急**：replace 不改变现状也不受阻；改库或改盘（走面板）二选一 |
  | `disk_dirty` | 磁盘被面板外手改脏 | replace 能纠正回库值（旧 conf 在面板操作日志有留底） |
  | `inconclusive` | 后端证明不了是 DSH | 不做判断；要结论走运维只读比对 conf.d |

## 现网踩过的坑（2026-10-21 首批两台实例）

按"症状 → 真因 → 怎么确认"排，都在真实环境里发生过。接口层面的事实（check/replace
的先后、HTTPS 行字段、`header_host` 口径）在 `docs/NG-API.md`。

| 症状 | 真因 | 怎么确认 |
|---|---|---|
| 详情页镜像/IP/状态显示成 `{.Config.Image}` 这类原文，实例被判 error | 命令模板用 `str.format` 渲染，Go 模板的 `{{…}}` 被收成 `{…}`，docker 不报错直接把原文打印 | 容器侧 `docker inspect --format '{{.State.Status}}' <名>` 与详情接口对表；解析器现在对含 `{}` 的字段一律判"看不到" |
| 容器 running/healthy，实例却永远挂着 error | error 是"上次动作失败"的痕迹，监视器只把 unhealthy 往回拉 | 看事件流：恢复会写 `state_recovered`，旧错误留在事件里；连续两轮 healthy 才恢复 |
| 释放卡在「面板上查不到 proxy_id=NNNN，拒绝盲删」 | frpc 掉线重连后 frp 面板会重建隧道行换 id，**proxy_id 是缓存不是身份** | 面板按名字查真身（`find_by_name`）；实测 20 分钟内同一隧道 2440→2475。释放会按（名字+客户端+remotePort）找回并纠正登记 |
| 续建时报「DNS 里已存在记录…重新创建实例以换新标签」 | 后一次失败的兜底回滚把前一次留下的外部 id 抹了 | 域名被占要看**记录值是否等于本站入口 IP**：等＝我们自己的，复用；不等＝别人家的，不复用也不删 |
| 续建时报「隧道 X 已存在但端口不一致」 | 端口探测只知"被占"，不知占着的就是我们自己上次建的那条 | 日志出现「沿用它的端口，不再新挑」即走对分支；指向别机的隧道一律拒绝复用 |
| `deploy.sh` 报 `required variable LLM_API_KEY is missing` | `.env` 里模型密钥必须控制台写入，且**容器内变量名与 .env 不同名**（`LLM_API_KEY`→`LLAMA_API_KEY`，`SEARCH_API_KEY`→`DEEPSEEK_API_KEY`），照容器里看到的名字去 .env 找一定找不到 | 密钥走 stdin 下发，绝不进命令行（命令行会进任务日志和 `ps`）；站点侧配 `credentials(kind=llm_key)` |
| verify 报"云端模型未禁用"，两台机器结论相反 | kit 脚本 `set -uo pipefail` + `printf \| grep -q`：grep 提前退出让 printf 吃 SIGPIPE，管道状态 141 变成假阴性/假阳性 | 别信脚本，信判定：控制台自己读 `dsh web --dump-config` 逐条核对（`domain/safety.py`），6 条云端路径必须 `disabled: true`，`web-deepseek-api` 必须**没被**禁用，`providers.local.baseURL` 必须等于本站 `llm_base_url` |
| 任务日志被上千行配置淹掉，部署过程看不见 | 自检命令读整份配置来判定，stdout 全量回流 | 这类命令走 `ctx.ssh(..., quiet=True)`：只留 `$ … -> exit N` 和一行判定结论 |

## 开通失败之后怎么看现场

- 第 60 步（真正动容器）之前失败：回滚按逆序删掉本次建的外部对象，每个删除只清自己
  那几列登记 id。
- 第 60 步之后失败：**不回滚**，现场原样留着，实例标 error。修完直接
  `POST /api/instances/{id}/deploy` 续跑——已建好的 DNS/隧道/站点会被认出来复用
  （日志里写"复用"），不会重复建，也不会顺手删。
- 兜底回滚不许抹掉"复用来的"对象登记：库里外部 id 只有在**本次真的新建过**时才清。

## 数据红线

释放与失败回滚都只允许 `docker stop`。任何路径都不出现 `docker rm` / `volume prune` /
删数据目录（集成测试把这条钉死在日志上）。要真删数据只有他自己在机器上动手。

**「DSH 配置」这格的取数口径**：详情接口**一次 ssh 都不做**（台账页要秒开），配置快照在
开通第 66 步与每次重启后各落一次，页面上「重新读取」按钮才现取（约 0.6–1 秒）。
读失败一律 502 并且**不动旧快照**——宁可显示"读取于三小时前"，也不能因为一次 ssh
超时把她已经配好的东西显示成没配。

**两个版本的坑**：`dsh --version`（运行时版本）与镜像 tag 不同源，卡上分开列，别当成
一个"版本"。配置快照的 `CONFIG_VERSION` 从 v1 升到 v2（新增了 `DSH` 这一组），
`add_config_snapshot` 按 `(instance_id, version)` upsert，沿用旧版本号会让老快照在新
文案下渲染出一屏空值。

docker exec <容器> sh -lc 'cd "${DSH_HOME:-/data}" && dsh web --dump-config | grep -A3 "id: agent-team"'
docker exec <容器> sh -lc 'ls -1 "${DSH_HOME:-/data}"/skills'          # 应看到 comfy-image

## 控制台自己的库备份

`dsh_control` 库存着每台实例的登录密钥与全部开通/释放档案，容器或库一出问题就一起没了。
`deploy/backup-console-db.sh` 每天 04:10 只 dump 这一个库（`pg_dump -Fc`，写完立刻
`pg_restore --list` 验目录读得出来，保留最近 14 份在 `~/backups/dsh-control/`）。
它跑在 PG 容器里用容器自带角色，脚本里不抄密码；**只碰 `dsh_control` 一个库**，
同一台 PG 实例上他的业务库一概不看、不导出。恢复：`pg_restore -d dsh_control --clean <文件>`。

## 控制台自己的公网入口

入口域名、隧道名、公网端口都记在 `docs/site/SEED.md`（真实值不进发布文档）。
链路：DNS A → frps 隧道 → nginxWebUI 站点（泛域名证书 + HTTP/2 + 80→443）→
控制台宿主机内网地址:13300。**公网只放行 443**：隧道端口没进安全组，也不该进——
把隧道端口开进公网等于绕过 TLS 和反代直接暴露内网服务。怀疑入口漂了，先跑
`python -m dsh_control.cli expose --dry-run`：它把三处对象逐一回读并打印
"已存在，跳过"，一个写请求都不发。

现网踩过两个身份坑，都出在"穿了两层反代之后你是谁"：

| 症状 | 真因 | 口径 |
| --- | --- | --- |
| 登录限速 5 次/分钟形同虚设，审计日志里的 IP 全是编的 | `client_ip()` 取 `X-Forwarded-For` **最左段**，而最左段是客户端自己写的 | 只信可信反代（回环 + 私网段，按 `peer_ip` 判定）送来的头；优先 `X-Real-IP`（反代用 `$remote_addr` 覆写，伪造不了），否则取 XFF **最右段**；对端不可信就只认 TCP 对端 |
| 一个人撞库可能把所有人关在门外 | 反过来的错：完全不看转发头，穿两层反代后所有人共用代理那一台 IP | 同上——按真人分桶。实测：同一真人带六个不同伪造头打登录，第六次仍 `429` |

会话 cookie 只在**这次请求走 TLS** 时才带 `Secure`（`X-Forwarded-Proto` 由可信
反代报）。一律 `Secure` 会把内网明文直连变成登不上；一律不带，则公网那枚能开
全部运维权限的 cookie 有机会跟着明文请求跑掉。
