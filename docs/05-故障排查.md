# 05 故障排查

面向排障现场的操作手册。架构约束在 `ARCHITECTURE.md`（§5.4 是 nginxWebUI），这里只放
"出了事怎么查、动手前怎么核对"。

## 库盘一致性核对（跑 `/api/nginx/replace` 之前必做）

`replace` 是全面板按库重建：`conf.d` 整目录重写、**库里没有的 conf 文件会被删掉**
（§5.4 红线）。库里任何与磁盘不一致的值都会被打回磁盘，所以重建前必须核对。

**控制台侧没有替代品的能力边界**：这一版 nginxWebUI 不提供任何读配置文件内容的接口
（`getFileContent` / `getFile` / `fileContent` / `confContent` 实测全 404），控制台也
没有 VPS 的 SSH。因此**磁盘真相只有运维只读比对一条路**，`drift_scan` 只能当旁证
（见下）。

### 运维只读比对（真正能证明一致性的做法）

1. 库侧：面板 API 分页读 `getPage` / `getLocationByServerId`（或运维直读 sqlite，
   `mode=ro`），取每条 location 的 `header_host`。
2. 盘侧：只读 `cat`/`grep` conf.d，取每个 server 文件里的 `proxy_set_header Host`。
3. 按站点名配对逐条比对。库里没有对应文件的（未发布/停用）与文件在库找不到的
   （**会被 replace 删除**）要单独列出。
4. 有漂移：只走面板把库改对（或确认盘上的手改是要保留的并回填库），绝不动文件系统。

最近一次实测（2026-10）：65 个 conf 文件、21 站点 + 25 upstream，可比对 10 条，
**0 漂移**——但前提是当时尚未有人手改；这条核对必须在每次 `replace` 前重做。

### `drift_scan` 黑盒旁证的口径与边界

控制台在 `replace` 前会跑 `drift_scan`：`https://<站点>/api/healthz` 带 `Origin` 探测，
与库里 `header_host` 对表。**状态码只有能证明后端是 DSH 时才是证据**：

- 证明通道只有两条：编排层传入的 `known_dsh` 登记名单；或响应带家族信封指纹
  （200 `{"ok": true}` / 401 `{"ok": false, "error": …}`，见 §4.1 错误清单）。
  真 DSH 的脏 Host 403 是裸文本，**不能**凭体证明，只能靠登记通道。
- 非 DSH 后端不是证据源：jellyfin/Gogs/llamaServer 拿到带端口的 Host 照样回
  200/401/502；onlyOffice 自家回 403。曾按状态码硬判，把三条库盘一致的
  `$host:$proxy_port` 站点误报成漂移（假警报），也把 onlyOffice 的 403 判成
  "一致"（假安全感）——两类错误都已修，证明不了的一律 `inconclusive`。
- 判定口径：`db_dirty`（仅适用于已确认为 DSH 的后端：库值带端口，replace 前必须先
  用 `patch_location` 修库）· `disk_dirty`（已证明 DSH、库净盘脏，replace 能纠正）·
  `consistent` · `inconclusive` · `unreachable` · `no_location`；默认只体检本控制台
  站点，他人站点仅在 `all_sites=True` 时列库值不判定。
- 结论进危险列表的只有 `db_dirty` / `disk_dirty`，且这两者都以"后端已证明是 DSH"
  为前提；`inconclusive` 的站点要下结论，回到上面的运维比对。
